# Agent 项目知识整理设计

## 目标

为 Codex 和其他代码 Agent 提供一套结构化的项目知识入口，使新会话能够快速理解项目，而不必反复扫描整个仓库、重读完整日志或重新推导已有结论。

这里的“节省 token”不是机械压缩文档长度，而是减少重复探索、重复分析和无关上下文读取。项目知识应足够完整，但需要按稳定程度和使用场景分层。

项目简介同时覆盖两类上下文：

- 工程上下文：代码架构、数据流、模块职责、测试与实验输出。
- 学习上下文：VLA 学习目标、阶段路线、已验证结论和后续方向。

## 选择的方案

采用三层项目知识结构：

```text
AGENTS.md
└── Agent 阅读顺序、按需加载规则和文档维护约定

docs/agent/
├── PROJECT_OVERVIEW.md
│   └── 稳定的项目目标、架构、关键决策与学习背景
├── CURRENT_STATUS.md
│   └── 动态的当前阶段、进行中工作、问题与下一步
└── PROJECT_STRUCTURE.md
    └── 目录职责、文件定位和新文件存放规则
```

相比单一大文档，这一方案避免每次加载大量动态或无关内容；相比只维护目录树，它能让 Agent 理解项目设计原因和研究背景，而不只是找到文件。

## `AGENTS.md`：自动入口与阅读路由

仓库根目录新增 `AGENTS.md`。它不复制项目正文，只保存长期有效的 Agent 工作规则：

1. 新任务开始时，先读 `docs/agent/PROJECT_OVERVIEW.md`。
2. 任务涉及当前阶段、实验延续或下一步决策时，再读 `docs/agent/CURRENT_STATUS.md`。
3. 任务涉及定位、创建、移动文件时，再读 `docs/agent/PROJECT_STRUCTURE.md`。
4. `BUGLOG.md`、`WORKLOG.md`、历史 specs/plans 和源码均按任务需要读取，不默认全文加载。
5. 修改架构、阶段状态或目录规则时，同步更新对应知识文档。

入口必须简短、稳定，不保存频繁变化的实验数字或逐日进展。

## `PROJECT_OVERVIEW.md`：稳定项目简介

`PROJECT_OVERVIEW.md` 是新 Agent 建立项目心智模型的核心文档，应说明：

### 项目定位

- 项目要解决的机器人与 VLA 问题。
- 工程验证、个人学习和简历成果之间的关系。
- 当前仓库覆盖的范围及明确不覆盖的范围。

### 系统数据流

描述从配置加载开始，经过仿真环境、图像采集、VLM 感知或 grounding、坐标变换、动作决策、控制执行，最终到评估指标和输出证据的完整流程。

### 模块职责

说明以下目录各自负责什么、主要依赖什么、通过什么接口协作：

- `src/vla_project/simulation/`
- `src/vla_project/vlm/`
- `src/vla_project/tools/`
- `tests/`
- `outputs/`
- `docs/`

### 关键设计决定与已验证结论

记录理解当前实现所必需的稳定事实，例如：

- 为什么从直接方向预测转向 grounding 与本体状态融合。
- 为什么世界坐标定位验证必须隔离真值。
- 为什么校准和独立验证需要分离。
- 已排除的主要错误方向，以及不应无证据重复尝试的方案。

这里只总结结论及其证据入口；完整实验过程继续保存在 `BUGLOG.md`、`WORKLOG.md` 和对应 specs/plans 中。

### 评价方法与学习路线

- 当前使用的核心指标、测试层级和实验通过标准。
- 已掌握、正在学习和计划验证的 VLA 能力。
- 关键代码、配置、测试和详细文档入口。

`PROJECT_OVERVIEW.md` 保存长期有效的项目知识。架构或研究方向发生实质变化时才更新，避免写成工作流水账。

## `CURRENT_STATUS.md`：动态工作快照

`CURRENT_STATUS.md` 保存继续当前工作的最小充分上下文：

- 最后更新时间。
- 当前阶段与本阶段目标。
- 最近完成且仍影响当前工作的事项。
- 正在进行的任务或实验。
- 尚未解决的问题与已知限制。
- 按优先级排列的下一步。
- 本阶段相关的代码、测试、配置、输出和文档入口。

状态变化时应改写失效内容，而不是无限追加。已经结束且只具历史价值的信息迁移到对应日志或计划，当前状态只保留仍然有效的事实。

## `PROJECT_STRUCTURE.md`：文件地图

沿用现有项目结构文档，职责限定为：

- 目录和代表文件的用途。
- 常见任务对应的代码与测试入口。
- 新源码、测试、文档和生成结果的存放规则。
- 不应提交或不应放在仓库根目录的内容。

项目背景、实验结论和动态进展不在这里重复记录，避免三份文档内容互相漂移。

## Agent 阅读流程

默认流程如下：

```text
启动任务
  -> 自动加载 AGENTS.md
  -> 阅读 PROJECT_OVERVIEW.md，建立整体心智模型
  -> 根据任务决定是否读取 CURRENT_STATUS.md
  -> 涉及文件定位或新增文件时读取 PROJECT_STRUCTURE.md
  -> 只打开与任务有关的源码、测试、日志或历史设计
```

`AGENTS.md` 负责路由，不要求所有任务无条件加载全部三份文档。这样既保证 Agent 有稳定背景，也避免简单任务携带不必要的动态上下文。

## 文档更新边界

| 变化类型 | 更新位置 |
| --- | --- |
| 项目目标、架构、数据流或关键设计结论改变 | `PROJECT_OVERVIEW.md` |
| 当前阶段、进行中工作、未解决问题或下一步改变 | `CURRENT_STATUS.md` |
| 目录、文件职责或新文件路由规则改变 | `PROJECT_STRUCTURE.md` |
| 详细实验过程和学习复盘 | `WORKLOG.md` |
| Bug 证据、根因、修复与验证 | `BUGLOG.md` |
| 单项功能的设计和执行步骤 | `docs/superpowers/specs/` 与 `docs/superpowers/plans/` |

同一事实只选择一个权威位置保存正文，其他文档只做简短摘要和链接。

## 实施范围

本次整理只做以下工作：

1. 新增根目录 `AGENTS.md`。
2. 新增 `docs/agent/PROJECT_OVERVIEW.md`。
3. 新增 `docs/agent/CURRENT_STATUS.md`。
4. 校对现有 `docs/agent/PROJECT_STRUCTURE.md` 与实际仓库的一致性。
5. 必要时在现有文档中补充入口链接，但不重写历史正文。

本次不批量拆分或移动 `BUGLOG.md`、`WORKLOG.md`、历史 specs/plans，也不删除历史记录。这样可以保留证据路径并避免无关的链接迁移。

## 正确性与验收

完成后应验证：

1. `AGENTS.md` 中的所有路径真实存在，阅读条件没有互相矛盾。
2. `PROJECT_OVERVIEW.md` 对模块、数据流和关键结论的描述可由当前源码、测试或历史证据支持。
3. `CURRENT_STATUS.md` 不包含已经失效的计划，且下一步有明确优先级。
4. `PROJECT_STRUCTURE.md` 的目录树与仓库当前状态一致。
5. 三份知识文档职责不重复，链接可解析，没有 `TODO`、`TBD` 或不明确占位符。
6. 从仓库根目录启动的新 Agent 能说明项目目标、当前阶段、主要模块和任务相关入口，而无需先扫描整个仓库。

## 非目标

- 不通过删减必要背景来追求最短文档。
- 不把所有历史细节复制进项目简介。
- 不用项目知识文档替代源码、测试或实验输出作为最终证据。
- 不要求每次任务全文读取所有文档。
